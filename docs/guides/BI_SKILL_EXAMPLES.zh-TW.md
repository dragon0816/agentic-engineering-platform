# BI 判讀規則（Skill）：五個領域的範例

給要向同事說明 Skill 的人。範例檔在 [`docs/examples/bi-skills/`](../examples/bi-skills/)。本頁的公司和內容都是虛構的。

## Skill 是什麼

Skill 是一頁給 AI 看的工作說明：讀某個資料夾的來源時，要做哪些卡、什麼算證據、什麼要留空、哪裡容易讀錯。它不是程式，也不會自己寫卡片。AI 讀完只產生候選卡，要由人審核後才寫入。

一份 Skill 有兩部分，效果差很多：

| 部分 | 做什麼 | 實測效果 |
|---|---|---|
| `card_types` | 這個領域可以做哪些卡 | **很大。** 沒有 Profile 也沒有 `card_types` 時，AI 只能做 Signal、Technology、Application 三種卡 |
| 規則文字 | 這個領域的判讀方式 | **較小但確實有。** 幫忙避開特定陷阱，同一份來源每次的結果仍會不同 |

Skill 改不了的事：AEP 的固定規則（沒有來源就不填、不編造）一定優先；AI 不能寫入 `verified`；`evidence_grade` 或 `confidence` 和卡片不同時，只會變成提案，由人決定。

## 五個範例

| 領域 | 看重的卡片 | 什麼算證據 | 最常見的陷阱 | 狀態 |
|---|---|---|---|---|
| AIDC | SupplyLink、RevenueFact、CustomerProduct | 明寫誰供給誰；同段出現不算 | 市場分母不同、預測當實績、展示當量產 | 已試跑 |
| 無線 | Ecosystem、Technology、Concept | 句子明寫的公司才算 | 把整段內容算給同一家、分類標題當產品 | 已試跑 |
| 機器人 | CustomerProduct、TestSolution、Application | 明寫的量測項目與階段 | 把「範例資料」當事實、自己打分數 | 已試跑 |
| 航太 | SupplyLink、CustomerProduct、Trend | 公司確認或具名報導 | 歷史案例當現況、宣布當部署 | 已試跑 |
| 手機 | CustomerProduct、Account、Signal | 官方規格、認證、實機拆解 | 傳聞當事實、不同版本混在一起 | **沒有試跑過** |

**手機這份目前不能使用。** 知識庫沒有 `applications/mobile` 資料夾，也沒有手機來源，這份規則只是示範寫法，沒有用真實資料驗證過。要先有資料夾和來源才能跑。

## 在知識庫哪裡看

`market-intel` 已放入這五份，**只供審閱，不會用在任何匯入**：`library/skill-review/skills/<領域>-extract-review/`。頁面的「進階：規則與程式」會列出，名稱以 `library/skill-review/` 開頭，「套用到」是 `library/skill-review/sources`，內容第一行寫著「僅供審閱，不會用在任何匯入」。

它們指向一個沒有來源的資料夾，所以任何匯入都選不到；也請不要把來源放進那個資料夾。知識庫的 `REPO.md` 會把它們列在「Skills in use」，那只是列表的標題，不代表正在使用。要真的採用某一份，照下面的「想新增規則」存成該領域自己的規則（`aidc` 已有 `aidc-extract`，要另外決定怎麼合併）。

## 怎麼改

位置在 Agent Web 的 BI 頁面。頁面正在改版，按鈕位置可能會移動。

1. **想改既有規則：** 在「進階：規則與程式」的規則列表按「和 AI 一起修改」，用白話說要改什麼，例如「公司自己沒確認的供貨，都寫進尚待確認」。AI 只提建議，要由你套用，套用後會存成新版本。
2. **想新增規則：** 按「新增擷取規則」，照範例檔填入。名稱寫 `<領域>/<名稱>`，例如 `wireless/wireless-extract`；再填套用的資料夾、卡片類型，規則內容貼 `---` 之後的部分。
3. **給大家用：** 存檔後只有你的電腦看得到，要 commit 再按「Push 給大家」。

範例檔開頭 `#` 開頭的那行是寫給同事看的，AI 讀不到，存進知識庫後也不會保留。

## 怎麼看效果

1. 挑 2 到 3 份這個領域的來源，改規則前後各按一次「試跑」。試跑不會寫入卡片。
2. 用「比較兩次試跑」看候選卡和欄位的差異。
3. **同一個版本多跑一次。** 同一份來源、同一份規則，實測候選卡數可以從 1 張變 8 張。差異沒有比兩次重跑的落差大，就不算規則的效果。
4. 每張候選卡都對照原文讀，不要只看張數。卡片變多不一定比較好，審核的工作量也會變多。

## 前後對照（虛構範例）

這些例子是虛構的，但呈現的是實測看到的同類差異。無線和機器人這兩列的差異，只靠 `card_types` 就看得到；AIDC 和航太標了次數的地方才是規則的效果。

| 領域 | 來源寫 | 沒有 Skill | 有 Skill |
|---|---|---|---|
| AIDC | 甲公司與乙公司共同展示一款電源櫃 | 只有 `card_types` 時，曾做成甲供貨給乙的 SupplyLink（2 次有 1 次）；沒有 Skill 也可能宣稱 `verified` | 不做供貨卡（4 次都沒有），也沒有宣稱 `verified` |
| 無線 | 丙公司主打企業 AP，丁公司主打入門級 | 兩家的內容都做成 Technology 或 Signal 卡 | 丙、丁各一張 Ecosystem 卡，每句只算在明寫的公司 |
| 機器人 | 一張測試方案頁，標著「範例資料，待驗證」 | 拆成 Signal、Application、Technology 三張，Signal 還寫出建議 | 一張 TestSolution，標記留在內容裡 |
| 航太 | 戊公司交付己公司，為歷史案例 | 做成 Technology 或 Signal，看不到供貨關係 | SupplyLink，並在尚待確認寫「目前是否仍供貨」（2 次都有；只有 `card_types` 時 2 次都沒有） |
| 手機 | （沒有資料，沒有試跑） | 不適用 | 不適用 |

## 實測看到的好與壞

共 74 次試跑，四個領域各 3 份來源，每份都比較「沒有 Skill、只有 `card_types`、完整 Skill」，每組跑 2 次。全部在暫存複本上進行，沒有寫入真正的知識庫。**次數很少，只能當方向，不是統計結果。**

**「沒有 Skill」要這樣理解：** 無線、機器人、航太沒有 Profile，所以只能做三種卡，大部分差異來自 `card_types`。AIDC 有 Profile，本來就能做 21 種卡，差異比較接近規則本身。

**好的：**
- 卡片種類變對：沒有 `card_types` 時，一張頁面常被拆成好幾張錯類型的卡。
- AIDC 不再宣稱 `verified`：沒有 Skill 2 次都有，只有 `card_types` 2 次有 1 次，完整 Skill 4 次都沒有。
- 航太的「來源未揭露」被保留：完整 Skill 2 次都有，只有 `card_types` 2 次有 1 次。

**壞的：**
- **`card_types` 列漏會丟資料。** AIDC 第一版漏了 CustomerProduct，來源明寫的產品全部抓不到。修正後只重跑了那份報告，三份小來源跑的是修正前的版本。
- **規則不一定被遵守。** 航太範例寫了不要改既有等級，模型仍然 4 次都提議調降一張已確認卡片的 `evidence_grade` 和 `confidence`（只有 `card_types` 和完整 Skill 各 2 次）。這些都只是提案，不會覆蓋，靠的是程式而不是規則。
- **結果不穩定。** AIDC「每家列名公司都要有卡」這條，同一份報告只抓到 2 張到 34 張，審核的提案數也沒有減少。
- **有時會多做或做錯。** 研究機構被做成生態系卡；一張概念頁被多做出一張測試方案卡；匯入檔名被填進 `source`；新公司的 `role` 是模型推論的（有標成推論）。
- **機器人的規則文字看不出效果。** 完整 Skill 和只有 `card_types` 的結果幾乎相同。

**這次測試的限制：** 只有 AIDC 有一份真正的報告。其他來源多半是已經寫好類型和欄位的卡片頁，比真實文件容易讀，所以這三個領域在真實報告上的效果還不知道。
